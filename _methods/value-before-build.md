## The rule

No agent build starts without a written value case. The value case states what will improve, by how much, and which assumptions must hold. The customer's business owner agrees to it before the first sprint.

## The steps

1. **Measure today.** Record how the work runs now: how often it happens, how long it takes, how often it goes wrong and what an error costs. Use the customer's own data where it exists.
2. **Describe the change.** State what the agent changes in the process. Name the steps it removes, shortens or checks.
3. **List the assumptions.** Write each assumption on its own line, with an owner and a way to test it. For example: "Planners accept at least half of the ranked options."
4. **Define the measure.** Choose the one number that proves the value after go-live, and who reports it.
5. **Set the stop condition.** State the result that would make us stop or change the build.

## Why

- **Assumptions are where value cases fail.** When they are explicit, the team tests the weakest one first.
- **The measure drives the design.** If the value comes from fewer errors, the agent must log every error it catches.
- **It protects the customer.** A build with no measurable value should stop at the design gate, not after test.

## What I do not publish

Value cases contain customer figures. This page shows the method only.
